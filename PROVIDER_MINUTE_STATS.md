# Документация `bin/update_provider_minute_stats.rb`

Скрипт читает историю операций из SQLite, рассчитывает показатели каждого
провайдера, обновляет таблицу `providers` и выводит подробный JSON-отчёт.
Это разовый пересчёт: для следующего обновления нужно запустить скрипт снова.
Историю операций предварительно заполняет движок роутинга или импортёр.
Скрипт не принимает файлы логов, CSV или JSON с операциями и сам не выбирает провайдера.

Расчёты вынесены в `lib/provider_minute_metrics.rb`. Описание сверено с кодом
05.09.2026.

## Запуск и параметры

Требуются Ruby, Bundler и зависимости из `Gemfile`, включая `sqlite3`.
Команды выполняются из корня проекта. Перед первым запуском установите
зависимости командой `bundle install`.

```powershell
bundle exec ruby bin/update_provider_minute_stats.rb --dry-run
bundle exec ruby bin/update_provider_minute_stats.rb
bundle exec ruby bin/update_provider_minute_stats.rb --database DB/operations.db --at 2026-07-29T12:41:18+03:00 --dry-run
bundle exec ruby bin/update_provider_minute_stats.rb --help
```

`--database PATH` выбирает существующую SQLite-базу; по умолчанию используется
`db/operations.db`, независимо от рабочего каталога. `--at` задаёт конец периода
с явным часовым поясом, по умолчанию используется текущее время.

Переданный относительный путь к базе отсчитывается от текущего рабочего каталога.
Примеры времени: `2026-09-05T12:00:00Z`, `2026-09-05T15:00:00+03:00`.
Позиционных аргументов нет. Для получения JSON-файла перенаправьте stdout:

```powershell
bundle exec ruby bin/update_provider_minute_stats.rb --dry-run > provider_stats.json
```

Обычный запуск добавляет недостающие колонки показателей и обновляет все записи
провайдеров одной транзакцией. Новую базу, таблицы и провайдеров он не создаёт.
`--dry-run` открывает базу только для чтения. Оба режима выводят JSON в stdout.

## Входные данные из базы

Нужны две существующие таблицы: `operations_history` и `providers`.
Таблицы очереди, решений, попыток и `analytics_metadata` этому скрипту не нужны.

### `operations_history`

Все перечисленные колонки должны существовать.

| Колонка | Ожидаемые данные |
|---|---|
| `operation_id` | ID операции; по модели проекта одна строка на операцию |
| `created_at` | Время создания, распознаваемое SQLite; `NULL` недопустим |
| `amount` | Число SQLite `integer` или `real` ≥ 0 в общей для проекта денежной единице |
| `payment_system_id` | ID существующей записи в `providers` |
| `status` | `approved`, `rejected`, `expired` или иной статус; `NULL` группируется как `unknown` |
| `latency_sec` | Число SQLite `integer` или `real` ≥ 0, либо `NULL`, если задержка неизвестна |
| `bank` | Банк для группировки; допускается `NULL` |

`card_brand` скрипту не требуется. Все статусы участвуют в количестве и сумме.
Значения статусов сравниваются точно, с учётом регистра. Повторные строки
не объединяются: при нестандартной схеме без уникальности `operation_id`
каждая строка будет посчитана отдельно.

### `providers`

| Колонки | Требование и роль |
|---|---|
| `payment_system_id`, `payment_system` | Обязательные колонки идентификатора и названия провайдера |
| `in_progress_count`, `in_progress_amount`, `conversion_24h`, `avg_latency_sec` | Обязательные существующие колонки для записи результата; прежние значения не используются в расчёте. Проверяются и при `--dry-run` |
| `traffic_percentage`, `volume_share_pct` | Необязательные числовые целевые доли количества и объёма, в процентах |
| `requests_per_minute_limit` | Необязательный числовой минутный лимит |
| `daily_approved_amount`, `daily_amount_limit`, `daily_turnover_min`, `daily_turnover_max` | Необязательные числовые данные снимка для расчёта дневных ограничений в JSON |
| `requests_last_minute` | Необязательная колонка назначения; скрипт её не создаёт |

Отсутствующие значения целей и лимитов дают `null` в зависящих от них расчётах.
Нулевой или отрицательный знаменатель также даёт `null`. При нулевой целевой
доле разность долей вычисляется, но процент выполнения цели — нет.

### Проверка данных и транзакция

1. Проверяется существование файла базы и обязательных колонок.
2. Во **всей истории** проверяется `created_at`: отсутствующая или нераспознаваемая
   дата вызывает ошибку, даже если запись не относится к расчётному периоду.
3. В интервале `[T − 24 часа, T]`, включая обе границы, проверяются ссылки на
   провайдеров, суммы и задержки. Запись ровно на нижней границе проверяется,
   но не входит в скользящее окно `last_24h`.
4. Рассчитывается отчёт. При обычном запуске добавляются недостающие колонки
   результатов и обновляются провайдеры. При ошибке изменения откатываются вместе.

Ожидание блокировки SQLite ограничено 5 секундами. Код не фильтрует провайдеров
по статусу: расчёт и обновление выполняются для всех записей `providers`.

## Запись в существующие поля

| Поле providers | Значение |
|---|---|
| `conversion_24h` | Число `approved` / число всех заявок за последние 24 часа; коэффициент 0…1 |
| `avg_latency_sec` | Среднее известных `latency_sec` за последнюю минуту, все статусы, округление до целых секунд |
| `requests_last_minute` | Число заявок за минуту; обновляется **только если колонка уже существует** |

`in_progress_count`/`in_progress_amount` этот скрипт **не пишет**: в проекте они
означают одновременно обрабатываемые заявки (см. `PaymentRouting::Rating::LoadFactorCalculator`
и hard-constraint "Лимит одновременных заявок"), а не поток заявок за минуту.
Минутный поток (то же значение, что раньше писалось в эти поля) остаётся только
в JSON-отчёте — `requests_last_minute` и `periods.minute.count`/`.amount`.

Пустая выборка даёт нулевые количество и сумму, но `NULL` для конверсии и среднего
времени. Повторный запуск заменяет значения актуальными, не прибавляет их.
Цели, лимиты и `daily_approved_amount` не изменяются.

## Добавляемые поля и их значения

При обычном запуске недостающие колонки ниже добавляются в `providers` через
`ALTER TABLE`. Первые 12 имеют тип `REAL`, `stats_calculated_at` — `TEXT`,
`stats_window_sec` — `INTEGER`. При `--dry-run` колонки не добавляются.

Все показатели этой таблицы относятся к последней минуте. В формулах
«все провайдеры» означает общую выборку операций за ту же минуту.

| Поле | Значение |
|---|---|
| `actual_count_share_pct` | 100 × количество провайдера / количество всех провайдеров |
| `actual_volume_share_pct` | 100 × сумма провайдера / сумма всех провайдеров |
| `approved_volume_share_pct` | 100 × одобренная сумма провайдера / одобренная сумма всех провайдеров |
| `count_target_fulfillment_pct` | 100 × `actual_count_share_pct` / `traffic_percentage` |
| `volume_target_fulfillment_pct` | 100 × `actual_volume_share_pct` / `volume_share_pct` |
| `count_share_gap_pp` | `actual_count_share_pct − traffic_percentage`, процентные пункты |
| `volume_share_gap_pp` | `actual_volume_share_pct − volume_share_pct`, процентные пункты |
| `approval_rate_pct` | 100 × количество `approved` / количество операций провайдера |
| `rejection_rate_pct` | 100 × количество `rejected` / количество операций провайдера |
| `expiration_rate_pct` | 100 × количество `expired` / количество операций провайдера |
| `approved_amount_pct` | 100 × сумма `approved` / сумма операций провайдера |
| `terminal_approval_rate_pct` | 100 × количество `approved` / количество `approved + rejected + expired` |
| `stats_calculated_at` | Конец окна расчёта `T` в UTC, ISO 8601 с микросекундами; при `--at` это указанное время |
| `stats_window_sec` | `60` |

Обновляется актуальное состояние провайдеров; отдельная история рассчитанных
снимков в базе не ведётся. Никакие строки `operations_history` не изменяются.

## JSON

`providers` содержит рассчитанные поля и следующие группы:

- `periods`: `minute`, `previous_minute`, `last_hour`, `last_24h`,
  `today_created_operations`. Каждая группа содержит количество, сумму, средний,
  минимальный и максимальный чек; количество, сумму и проценты каждого статуса;
  успешность по количеству и сумме; доли провайдера по количеству, сумме и успешной
  сумме; успешность среди завершённых операций; среднее, медиану и p95 задержки
  отдельно для всех известных значений и для успешных операций.
- `minute_change`: разница количества и суммы с предыдущей минутой, в абсолютных
  значениях и процентах.
- `targets`: отклонения фактических долей от целей в процентных пунктах,
  использование и остаток минутного лимита; использование и остаток дневного
  лимита и выполнение дневных обязательств по **имеющемуся снимку провайдера**.
- `minute_breakdown`: те же показатели по банкам и диапазонам суммы за минуту.
  Доли этих групп считаются внутри текущего провайдера. Диапазоны не пересекаются:
  `[0,1000)`, `[1000,10000)`, `[10000,50000)`, `[50000,100000)`, `[100000,+∞)`.

`totals` содержит сводные метрики всех провайдеров для каждого периода. `windows`
явно задаёт границы. `persistence` перечисляет поля записи и режим запуска.
`definitions` содержит определения показателей и ограничения интерпретации.

| Поле `persistence` | Значение |
|---|---|
| `dry_run` | Включён ли режим без записи |
| `columns` | Полный список колонок, которые обновляет обычный запуск |
| `columns_to_add` | Колонки, отсутствовавшие перед расчётом; в обычном режиме они добавлены, в `--dry-run` только перечислены |
| `schema_changed` | Менялась ли схема в этом запуске; всегда `false` при `--dry-run` |

Верхнеуровневые `window_start_exclusive` и `window_end_inclusive` задают минутное
окно. `providers` — массив результатов, упорядоченный по `payment_system_id`.
`requests_last_minute` присутствует в JSON независимо от наличия колонки в базе.

## Формулы и периоды

- Доля количества = `100 × count_provider / count_all`.
- Доля суммы = `100 × amount_provider / amount_all`.
- Доля успешной суммы = `100 × approved_amount_provider / approved_amount_all`.
- Успешность = `100 × approved_count / count_provider`; аналогично для отказов
  `rejected` и истечений `expired`.
- Успешность по сумме = `100 × approved_amount_provider / amount_provider`.
- Успешность среди завершённых = `100 × approved / (approved + rejected + expired)`.
  Другие статусы не считаются завершёнными.
- Изменение к предыдущей минуте = `100 × (current - previous) / previous`.
- Отклонение от цели = `actual_pct - target_pct`, в процентных пунктах.
- p95 определяется методом ближайшего ранга: элемент `ceil(0.95 × n)`
  отсортированного списка. Для медианы чётного списка берётся среднее двух средних.

Доли и проценты статусов лежат в диапазоне 0…100. Изменения, отклонения,
выполнение целей и загрузка лимитов могут выходить за эти границы.
Проценты, разности долей, средний чек и средние задержки в группах округляются
до четырёх знаков; сохраняемый `conversion_24h` остаётся коэффициентом 0…1
без такого округления. `avg_latency_sec` округляется до целых секунд.
Нулевой или отсутствующий знаменатель даёт `null`, не 0%. Нулевой/отсутствующий
лимит также даёт `null`. Отрицательный остаток лимита означает превышение.
Всегда доступны количества наблюдений для оценки устойчивости процентов.

Например, за минуту у всех провайдеров было 20 операций, у одного — 5,
из них 4 `approved`. При целевой доле количества 20% его
`actual_count_share_pct = 25`, `count_target_fulfillment_pct = 125`,
`count_share_gap_pp = 5`, `approval_rate_pct = 80`.

Скользящие окна: `(конец - длительность, конец]`; предыдущая минута:
`(конец - 120 секунд, конец - 60 секунд]`. Календарный день считается по UTC,
`[00:00 UTC, конец]`. Метки с UTC-смещением нормализуются SQLite; метки без
смещения SQLite трактует как UTC. Пропуски задержки не превращаются в нули.

## Ограничения исходных данных

Источником служит `operations_history.created_at`. Одна запись означает одну
зарегистрированную заявку провайдеру: фактических HTTP-обращений и повторных
отправок она не отражает. `--at` использует текущие сохранённые статусы, а не
восстанавливает состояние заявки в прошлом.

Минутный поток (`requests_last_minute`/`periods.minute`) - это не то же самое,
что одновременно обрабатываемые заявки (`in_progress_count`/`in_progress_amount`
в остальном проекте) - см. раздел выше. Скрипт не рассчитывает загрузку
относительно лимитов одновременной обработки, только относительно
`requests_per_minute_limit` (см. `targets.requests_limit_utilization_pct`).

Время завершения выплат отсутствует. Дневная сумма `approved` в отчёте относится
к заявкам, **созданным** за день, поэтому не заменяет `daily_approved_amount`.
Свежесть снимка провайдера и полноту истории база не удостоверяет. Минутные
статусы недавно созданных заявок могут ещё измениться.

Метрики, не перечисленные в разделах записи выше, остаются только в JSON.
Фактические доли не записываются в `traffic_percentage` и `volume_share_pct`,
поскольку это настройки целей. Для полного журнала повторных отправок текущих
данных недостаточно.

## Ошибки и коды завершения

При успешном расчёте код завершения — `0`. Обрабатываемые ошибки выводятся
в stderr с префиксом `Minute statistics update failed:`, код завершения — `1`.
Изменения схемы и значений при ошибке внутри транзакции откатываются.

| Сообщение или ситуация | Что проверить |
|---|---|
| `Database does not exist` | Путь из `--database`; база должна быть создана заранее |
| `missing columns` | Наличие обязательных колонок в таблицах, в том числе четырёх существующих полей назначения |
| `Invalid or missing operations_history.created_at` | Дату указанной операции; проверка охватывает всю историю |
| `Missing provider or invalid amount/latency for operation` | Существование провайдера, числовые типы и неотрицательные значения суммы/задержки |
| `--at must include Z or a UTC offset` | Часовой пояс в аргументе времени |
| Ошибка SQLite при записи | Права записи, блокировку базы, ограничения или триггеры |

Если итоговые значения нулевые, проверьте попадание `created_at` в окно:
обычный запуск считает относительно текущего времени. Для старой тестовой
истории задайте подходящий `--at`; такой запуск без `--dry-run` заменит
показатели в базе результатами на указанное время.

## Совместимость с остальным проектом

Исходная схема из `DB/create_tables.rb` подходит для этого скрипта.
Однако после обычного запуска добавленные колонки нарушают строгую проверку
схемы в `bin/analyze_db.rb` / `CanonicalDatabaseSource`: тот отклонит базу,
пока его проверка не адаптирована. `--dry-run` исходную схему сохраняет,
но не удаляет колонки, добавленные ранее.

Набор `test/provider_minute_stats_test.rb` содержит проверки границ окон,
метрик, некорректных данных, повторного пересчёта, отката и `--dry-run`.
Его запуск: `bundle exec ruby test/provider_minute_stats_test.rb`.
Тесты используют временную копию `DB/operations.db` и зависят от её схемы
и имеющихся провайдеров.

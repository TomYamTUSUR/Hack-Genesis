Ты работаешь над задачей хакатона:

«Задача 2. Умный роутинг выплат».

Этот текст является техническим заданием и source of truth для реализации.
При проектировании и написании кода необходимо сверяться с ним.

Не изменяй смысл требований.
Если какое-либо поведение не определено в ТЗ, не придумывай его молча:
явно укажи допущение и отдели его от обязательных требований задачи.


==================================================
1. ЦЕЛЬ ЗАДАЧИ
==================================================

Необходимо разработать механизм умного распределения выплат
между несколькими платёжными партнёрами.

Для каждой новой операции система должна:

1. выбрать наиболее подходящего платёжного партнёра
   с учётом стратегии и правил;

2. если выбранный партнёр не может провести выплату,
   отказывает в обработке или не подходит —
   автоматически перейти к следующему подходящему варианту;

3. сохранить понятное объяснение принятого решения:

   - какие варианты рассматривались;
   - почему был выбран конкретный партнёр;
   - почему остальные партнёры были исключены;

4. на основе истории операций оценивать качество
   текущего роутинга;

5. формировать рекомендации.

==================================================
3. ОСНОВНАЯ МОДЕЛЬ РЕШЕНИЯ
==================================================

Логика роутинга должна быть разделена на два уровня:

1. Hard Constraints
2. Soft Goals / Routing Strategy


Последовательность обработки:

Input
    ↓
Hard Constraints
    ↓
Eligible Providers
    ↓
Routing Strategy / Soft Goals
    ↓
Selected Provider
    ↓
Result / Fallback


Hard Constraints отвечают на вопрос:

«Можно ли вообще отправить эту заявку
этому провайдеру?»


Soft Goals отвечают на вопрос:

«Какого провайдера предпочтительнее выбрать
среди уже допустимых?»


ВАЖНО:

Hard Constraints всегда применяются ДО выбора стратегии.

Никакая стратегия или soft-goal
не может нарушить Hard Constraint.

4. КЛЮЧЕВЫЕ ПОЛЯ PROVIDER
==================================================

Основные поля providers.json:


traffic_percentage

Целевая доля провайдера
по количеству заявок.


limit_amount_min
limit_amount_max

Минимальная и максимальная сумма заявки,
которую может обработать провайдер.


daily_amount_limit

Максимальный дневной оборот провайдера.


daily_approved_amount

Уже проведённый дневной оборот.


in_progress_count_limit

Максимальное количество одновременно
обрабатываемых заявок.


in_progress_count

Текущее количество заявок in-progress.


in_progress_amount_limit

Максимальная сумма заявок,
которые одновременно могут находиться in-progress.


in_progress_amount

Текущая сумма заявок in-progress.


available_requisites

Количество свободных реквизитов / терминалов.


banks

Список поддерживаемых банков.


exclude_banks

Список исключённых банков.


conversion_24h

Конверсия провайдера за последние 24 часа.


provider_margin_pct

Маржа провайдера.


merchant_margin_pct

Маржа мерчанта.

daily_amount_limit.


Эти значения могут:

- быть вычислены из истории;
- быть заданы командой как реалистичные значения.


==================================================
6. HARD CONSTRAINTS
==================================================

Hard Constraints являются обязательными.

Если хотя бы одна проверка не выполнена,
провайдер исключается из рассмотрения
независимо от выбранной стратегии.


--------------------------------------------------
6.1 Provider Status
--------------------------------------------------

Если:

provider.status != "active"

провайдер должен быть исключён.


--------------------------------------------------
6.2 Amount Range
--------------------------------------------------

Если сумма операции находится вне:

limit_amount_min
limit_amount_max

провайдер должен быть исключён.


--------------------------------------------------
6.3 Daily Amount Limit
--------------------------------------------------

Проверить:

daily_approved_amount + operation.amount
    <= daily_amount_limit

Если лимит будет превышен,
провайдер исключается.


--------------------------------------------------
6.4 In-Progress Limits
--------------------------------------------------

Проверять:

in_progress_count_limit

и:

in_progress_amount_limit

Если новая операция приведёт
к превышению лимитов одновременных заявок
или их денежного объёма,
провайдер исключается.


--------------------------------------------------
6.5 Bank Filter
--------------------------------------------------

Банк операции должен соответствовать:

banks

и не должен попадать в:

exclude_banks.


--------------------------------------------------
6.6 Margin Constraint
--------------------------------------------------

Если:

provider_margin_pct > merchant_margin_pct

то провайдер не должен использоваться,

если отсутствует специальное соглашение:

allow_negative_agreement.


--------------------------------------------------
6.7 Available Requisites
--------------------------------------------------

Если:

available_requisites == 0

провайдер исключается.


--------------------------------------------------
6.8 Rate Limit
--------------------------------------------------

Если превышен:

requests_per_minute_limit

провайдер исключается.


==================================================
7. ROUTING STRATEGIES
==================================================

Решение должно поддерживать несколько
стратегий роутинга.

Также должна поддерживаться
комбинация нескольких стратегий.


--------------------------------------------------
7.1 Процент от количества заявок
--------------------------------------------------

Критерий:

доля по числу операций.

Пример:

vipay      40%
payflow    35%
quickpay   25%

Система должна стремиться поддерживать
целевое распределение количества заявок.


--------------------------------------------------
7.2 Процент от денежного объёма
--------------------------------------------------

Критерий:

доля по сумме операций,
а не по количеству.

Пример:

vipay      50% денежного оборота
остальные  50%


--------------------------------------------------
7.3 Очередь в каскаде
--------------------------------------------------

Провайдеры обходятся последовательно
согласно полю priority.

Пример:

vipay
    ↓ при отказе
payflow
    ↓ при отказе
quickpay


--------------------------------------------------
7.4 Маршрутизация по сумме чека
--------------------------------------------------

Провайдер выбирается
в зависимости от диапазона суммы операции.

Пример:

500 – 50 000
    → payflow

50 001 – 100 000
    → vipay

> 100 000
    → quickpay


--------------------------------------------------
7.5 Приоритизация по конверсии
--------------------------------------------------

Использовать:

conversion_24h

Провайдер с более высокой конверсией
может получать повышенный приоритет.

Это soft-boost,
а не нарушение Hard Constraints.


--------------------------------------------------
7.6 По интенсивности
--------------------------------------------------

Учитывать ограничения
по количеству заявок в минуту
для терминала / провайдера.

Пример:

Terminal A:
не более 7 заявок / минуту

Terminal B:
не более 15 заявок / минуту


--------------------------------------------------
7.7 По финансовым обязательствам
--------------------------------------------------

Учитывать минимальный
и максимальный дневной оборот.

Пример:

payflow:

не менее 2 000 000 ₽ / сутки

vipay:

не более 5 000 000 ₽ / сутки


==================================================
8. SOFT GOALS
==================================================

Soft Goals не запрещают использование провайдера.

Они должны повышать или понижать
его приоритет среди провайдеров,
которые уже прошли Hard Constraints.


--------------------------------------------------
8.1 Target Count Share
--------------------------------------------------

Поле:

traffic_percentage

Если провайдер получает меньше
своей целевой доли заявок:

→ его приоритет повышается.

Если получает больше:

→ приоритет понижается.


--------------------------------------------------
8.2 Target Volume Share
--------------------------------------------------

Поле:

volume_share_pct

Аналогично traffic_percentage,
но доля рассчитывается
по денежному объёму.


--------------------------------------------------
8.3 Conversion
--------------------------------------------------

Поле:

conversion_24h

Более высокая конверсия
может повышать приоритет,
если активная стратегия
учитывает conversion.


--------------------------------------------------
8.4 Cascade Priority
--------------------------------------------------

Поле:

priority

Определяет очередность
при каскадной / priority-стратегии.


--------------------------------------------------
8.5 Minimum Daily Turnover
--------------------------------------------------

Поле:

daily_turnover_min

Если минимальный дневной оборот
провайдера ещё не набран,
его приоритет может повышаться.


==================================================
9. СОГЛАСОВАНИЕ СТРАТЕГИЙ
==================================================

Различные критерии могут конфликтовать.

Система обязана:

1. разделять Hard Constraints и Soft Goals;

2. применять Hard Constraints
   ДО выбора стратегии;

3. выбирать кандидата
   только внутри допустимого provider pool;

4. поддерживать активную стратегию
   или комбинацию стратегий;

5. при конфликте Soft Goals
   использовать ЯВНЫЙ приоритет политик;

6. фиксировать разрешение конфликта
   в attempts и/или аналитическом отчёте;

7. при fallback снова соблюдать
   все Hard Constraints.


==================================================
10. ПРИМЕР КОНФЛИКТА
==================================================

Условия:

Цель:

40% заявок должны идти на vipay.

Но:

vipay почти исчерпал daily max.

Одновременно:

payflow имеет финансовое обязательство:

не менее 2 000 000 ₽ / сутки.


Ожидаемое поведение:

1. Router снижает долю vipay.

2. Router повышает приоритет payflow,
   чтобы приблизиться к его
   минимальному дневному обороту.

3. В аналитике / attempts
   объясняется причина такого решения.


==================================================
11. FALLBACK
==================================================

Если выбранный провайдер:

- отказал;
- не смог провести выплату;
- получил timeout;

необходимо:

1. исключить его из пула
   для текущей операции;

2. выбрать следующего
   подходящего провайдера;

3. не нарушать Hard Constraints;

4. сохранить информацию
   о предыдущей попытке.


Если пул подходящих провайдеров пуст:

использовать fallback:

spacepayments

как self-provider.


==================================================
12. ОБНОВЛЕНИЕ СОСТОЯНИЯ
==================================================

После каждой обработанной заявки
необходимо обновлять состояние
выбранного провайдера.

Минимально должны обновляться:

- текущая загрузка;
- оборот;
- счётчики интенсивности.

При расчёте следующих операций
использовать уже обновлённое состояние.

Таким образом операции очереди
обрабатываются с учётом результатов
предыдущих операций.


==================================================
13. EXPLAINABILITY
==================================================

Для каждой выплаты должно сохраняться
понятное объяснение решения.

Необходимо показать:

- какие провайдеры рассматривались;
- какие провайдеры были исключены;
- почему они были исключены;
- какой провайдер был выбран;
- почему именно он был выбран;
- какие fallback attempts произошли.


Каждый skipped provider должен иметь:

decision
reason
details


Пример:

{
  "provider": "vipay",
  "decision": "skipped",
  "reason": "amount_exceeds_limit",
  "details": "150000 > limit_amount_max 100000"
}


Выбранный provider должен быть
также отражён в attempts.

Пример:

{
  "provider": "quickpay",
  "decision": "selected",
  "reason": "only_eligible_provider"
}

[
  {

        "reason": "only_eligible_provider"
      }

    "simulated_result": "approved",

  }

Основные поля:

operation_id

selected_provider

attempts

simulated_result

latency_sec


Формат необходимо сверять
с sample_routing_decisions.json
и validate.rb.

15. ANALYTICS
==================================================

На основании истории операций
и результатов нового роутинга
необходимо оценивать качество решения.

Исторические данные разрешается использовать
для вычисления:

- conversion;
- count share;
- volume share;
- калибровки алгоритма.


Система также должна давать рекомендации
по текущему роутингу.


Точный расширенный формат рекомендаций
в ТЗ не зафиксирован.

Если добавляется собственный формат аналитики,
он не должен ломать обязательный
routing_decisions.json.


==================================================
16. ОСНОВНОЙ ALGORITHM FLOW
==================================================

Для каждой operation:

1. Получить актуальное состояние providers.

2. Применить все Hard Constraints.

3. Для каждого исключённого provider
   сохранить reason и details.

4. Сформировать Eligible Provider Pool.

5. Рассчитать необходимые Soft Goals
   и показатели активной стратегии.

6. Если используются несколько стратегий,
   разрешить их конфликт
   согласно явному приоритету политик.

7. Построить ranking допустимых providers.

8. Выбрать первого кандидата.

9. Выполнить / симулировать попытку.

10. Сохранить attempt.

11. При успехе:
    завершить маршрутизацию операции.

12. При отказе / timeout:
    исключить текущего provider
    и выбрать следующего из допустимого пула.

13. Если provider pool пуст:
    использовать spacepayments.

14. Обновить метрики и состояние providers.

15. Перейти к следующей operation.

16. После обработки очереди
    сформировать routing_decisions.json.

17. Проверить результат через validate.rb.

18. На основе истории и результатов
    сформировать оценку качества роутинга
    и рекомендации.


==================================================
17. ПРИНЦИПЫ, КОТОРЫЕ НЕЛЬЗЯ НАРУШАТЬ
==================================================

HARD CONSTRAINTS > SOFT GOALS.

Ни одна стратегия не может вернуть provider,
который не прошёл Hard Constraints.

Fallback также обязан повторно соблюдать
Hard Constraints.

Soft Goals должны влиять на приоритет,
а не превращаться в жёсткое ограничение,
если обратное прямо не указано ТЗ.

Конфликты нескольких Soft Goals
должны разрешаться явно и объяснимо.

Каждое решение должно быть воспроизводимым
и объяснимым через attempts.

Состояние providers необходимо обновлять
после обработки операций.

Итоговый JSON должен проходить validate.rb.

18. ПРАВИЛА РАБОТЫ С ЭТИМ ТЗ
==================================================

Когда реализуешь новую часть проекта:

1. сначала найди соответствующее требование
   в этом ТЗ;

2. определи:
   - Hard Constraint это;
   - Soft Goal;
   - Strategy;
   - Fallback;
   - Output;
   - Analytics;

3. не смешивай Hard Constraints
   со scoring / strategy logic;

4. если требование неоднозначно —
   сообщи об этом;

5. если предлагаешь дополнительную функцию —
   отдельно пометь её как extension,
   а не обязательное требование;

6. сохраняй совместимость
   с входными файлами data/;

7. сохраняй совместимость
   с validate.rb;

8. не меняй обязательный формат результата
   без предварительной проверки валидатора.

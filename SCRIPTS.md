# Описание скриптов проекта

В документе описаны все 14 Ruby-файлов проекта: команды для работы с базой данных, валидатор, библиотеки и тесты. Описания соответствуют реализации в исходном коде.

Примеры команд выполняются из корня проекта. Для установки зависимостей из `Gemfile` используется `bundle install`. Команды из `bin/` поддерживают `--help`; пути по умолчанию вычисляются относительно проекта, а переданные относительные пути — относительно текущего рабочего каталога.

## Создание базы данных

### `DB/create_tables.rb`

Создаёт SQLite-файл `DB/operations.db`, если его ещё нет, и восемь таблиц:

- `providers` — провайдеры, их ограничения и метрики;
- `operations_queue` — очередь заявок и реквизиты;
- `operations_history` — история операций;
- `routing_decisions` — выбранные провайдеры и результаты;
- `routing_attempts` — последовательность попыток;
- `eligible_providers` — допустимость провайдеров для заявки;
- `provider_skip_reasons` — причины пропуска провайдеров;
- `reference_decisions` — эталонные решения.

Включает внешние ключи для своего соединения и выводит список таблиц. Использует `CREATE TABLE IF NOT EXISTS`: существующие таблицы и данные сохраняются, но структура уже созданных таблиц не обновляется. Исходные JSON и CSV этот скрипт не загружает. Аргументов командной строки нет.

```powershell
bundle exec ruby DB/create_tables.rb
```

## Импорт и запись данных

### `bin/import_data.rb`

Загружает исходные данные в уже существующую базу со схемой из `DB/create_tables.rb`. Переносит провайдеров, историю, очередь, детерминированные эталонные решения, списки допустимых провайдеров и ожидаемые причины пропуска.

Читает из `data/`: `providers.json`, `operations_history.csv`, `reference_decisions.json` и `operations_queue.json`, а при отсутствии последнего — `operations_queue_10.json`. По флагу `--include-sample` дополнительно загружает демонстрационные решения и попытки из `sample_routing_decisions.json`.

Добавляет только отсутствующие записи: существующие значения и идентификаторы сохраняются. Весь импорт выполняется в транзакции и откатывается при ошибке. Схема не меняется; метаданные `snapshot_at`, `gateway`, `merchant` и описание эталонов не сохраняются, поскольку для них нет колонок. Выводит число добавленных и пропущенных записей по таблицам.

Параметры: `--database PATH`, `--data-dir PATH`, `--include-sample`. По умолчанию используются `DB/operations.db` и каталог `data/`.

```powershell
bundle exec ruby bin/import_data.rb
bundle exec ruby bin/import_data.rb --include-sample
```

### `bin/import_sources.rb`

Импортирует данные через `RoutingAnalytics::DatabaseWriter`: метаданные снимка, провайдеров, историю, очередь и детерминированные эталонные решения. В отличие от `import_data.rb`, обновляет записи при совпадении ключей. Удаляет из очереди операции, загруженные в историю, и не возвращает туда уже обработанные заявки. Работает транзакционно и выводит количество обработанных записей.

По умолчанию читает `data/providers.json`, `data/operations_history.csv`, `data/operations_queue_10.json`, `data/reference_decisions.json` и пишет в `DB/operations.db`. Пути задаются через `--providers`, `--history`, `--queue`, `--references`, `--database`.

Требует отдельной совместимой схемы с таблицей `analytics_metadata`; сам таблицы не создаёт. База, созданная только `DB/create_tables.rb`, для него не подходит. Ожидаемые списки допустимости и причин пропуска из эталонного JSON этот импортер не переносит.

```powershell
# Для заранее подготовленной совместимой базы:
bundle exec ruby bin/import_sources.rb --database path/to/analytics.db
```

### `bin/log_operations.rb`

Сохраняет уже рассчитанные результаты роутинга. Получает JSON с операциями в формате очереди и JSON с решениями в формате примера результата. Проверяет отсутствие повторных `operation_id` и совпадение наборов операций и решений.

Одной транзакцией обновляет историю и решения, заменяет попытки, признаки допустимости и причины пропуска для каждой операции, затем удаляет операцию из очереди. Повторная запись заменяет её актуальное состояние. Выбор провайдера и симуляцию выплаты скрипт не выполняет.

Обязательные параметры: `--operations PATH`, `--decisions PATH`. Необязательный: `--database PATH`, по умолчанию `DB/operations.db`. Использует `DatabaseWriter` и требует совместимой схемы с `analytics_metadata` и связями, допускающими удаление обработанной заявки из очереди.

```powershell
bundle exec ruby bin/log_operations.rb --database path/to/analytics.db --operations incoming/operations_queue.json --decisions incoming/routing_decisions.json
```

## Статистика и отчёты

### `bin/update_provider_minute_stats.rb`

Пересчитывает показатели каждого провайдера по `operations_history` за интервал **(момент расчёта − 60 секунд, момент расчёта]**. Учитывает часовые пояса и все статусы операций.

Записывает в `providers`:

- `requests_last_minute` — количество записей истории за минуту; при первом запуске добавляет эту колонку;
- `in_progress_count` — количество уникальных операций за ту же минуту;
- `in_progress_amount` — сумму этих операций.

В этой реализации поля `in_progress_*` отражают все заявки за минуту, независимо от статуса, а не общее число и сумму незавершённых операций. Если заявок в интервале нет, значения обнуляются. Это разовый пересчёт, а не постоянно работающий процесс. Проверяет исходные даты, а в выбранном интервале — суммы и ссылки на провайдеров; изменение схемы и значений выполняет транзакционно. Выводит JSON с границами окна и результатами.

Параметры: `--database PATH` (по умолчанию `DB/operations.db`) и `--at ISO8601` (по умолчанию текущее время). В `--at` обязателен `Z` или сдвиг UTC.

```powershell
bundle exec ruby bin/update_provider_minute_stats.rb --at 2026-07-29T08:01:00+03:00
```

Добавленная колонка несовместима со строгой проверкой исходной схемы в `analyze_db.rb`: после такого обновления тот отклонит базу до адаптации своего проверяющего кода.

### `bin/analyze.rb`

Читает SQLite-базу через `RoutingAnalytics::DatabaseSource`, рассчитывает отчёт через `Analyzer` и сохраняет JSON в `reports/routing_report.json`. Содержит распределение заявок и денежных объёмов по провайдерам и дням, статусы, конверсию, время обработки, загрузку лимитов, причины пропуска, сведения об очереди, рекомендации и проверки качества данных.

Базу открывает только для чтения. Требует схему с `analytics_metadata`, используемую `lib/routing_analytics.rb`; схема из одного `DB/create_tables.rb` не подходит.

Параметры: `--database PATH` (по умолчанию `DB/operations.db`), `--output PATH`, `--stdout`. Последний выводит отчёт в консоль без записи файла. Запись отчёта внутрь `data/` и `scripts/` запрещена кодом.

```powershell
bundle exec ruby bin/analyze.rb --database path/to/analytics.db
```

### `bin/analyze_db.rb`

Формирует аналитический JSON по исходной схеме из восьми таблиц, созданной `DB/create_tables.rb`. Использует `CanonicalDatabaseAnalytics`: проверяет точный набор таблиц, порядок и названия колонок, а также внешние ключи. Читает базу без изменений и по умолчанию сохраняет `reports/routing_report_db.json`.

Для расчётов использует общий `Analyzer`. Объединяет причины пропуска из `provider_skip_reasons` и пропущенных `routing_attempts`, исключая дубли по операции, провайдеру и причине. Если `provider_skip_reasons` заполнена эталонными ожиданиями через `import_data.rb`, эти ожидания тоже попадут в счётчики: их нельзя автоматически считать фактическими отказами. Метаданные снимка, шлюза и мерчанта остаются `null`, поскольку в этой схеме они не хранятся.

Параметры: `--database PATH` (по умолчанию `DB/operations.db`), `--output PATH`, `--stdout`. Запись отчёта внутрь `data/`, `scripts/` и `DB/` запрещена кодом. Дополнительная таблица или колонка, включая `requests_last_minute`, вызывает ошибку проверки схемы.

```powershell
bundle exec ruby bin/analyze_db.rb
bundle exec ruby bin/analyze_db.rb --stdout
```

## Проверка решений

### `scripts/validate_10.rb`

Проверяет переданный JSON с решениями для десяти заявок из `data/operations_queue_10.json`. Также читает `providers.json` и `reference_decisions.json`.

Проверяет обязательные поля решения и попыток, покрытие очереди, детерминированные случаи и допустимость выбранного провайдера по текущему снимку: статус, долю трафика, диапазон суммы, дневной лимит, ограничения in-progress, реквизиты, маржу и банки. Для известных случаев проверяет наличие попытки со статусом `skipped`; точное совпадение текста причины с эталоном не проверяет.

Печатает результаты, ошибки и предупреждения. Возвращает код `0`, если ошибок нет, иначе `1`; одни предупреждения не означают провал. Базу и входные файлы не меняет.

Ограничения: не обновляет состояние провайдеров последовательно между заявками, не проверяет минутный лимит запросов и не оценивает качество стратегий. Поэтому успешная проверка не доказывает выполнение всего ТЗ.

Единственный обязательный аргумент — путь к JSON с решениями:

```powershell
ruby scripts/validate_10.rb data/sample_routing_decisions.json
```

## Библиотеки

Эти файлы подключаются через `require_relative`; самостоятельного интерфейса командной строки у них нет.

### `lib/routing_analytics.rb`

Основная библиотека аналитики и хранения данных. Содержит:

- `Loader` — чтение и проверку JSON/CSV;
- `DatabaseSource` — чтение БД с `analytics_metadata` и подготовку данных для анализа;
- `DatabaseWriter` — транзакционный импорт и запись результатов роутинга;
- `Analyzer` — объединение истории и актуальных решений без двойного подсчёта операций, расчёт распределений, конверсии, задержек, лимитов, очереди, рекомендаций и качества данных;
- `ReportWriter` — сохранение JSON-отчёта;
- `PathGuard`, `Utils`, `Error` — защиту путей записи, вспомогательные вычисления и ошибки.

Используется командами `import_sources.rb`, `log_operations.rb`, `analyze.rb`, а также библиотекой канонической аналитики. Не реализует самостоятельный маршрутизатор выплат.

### `lib/canonical_database_analytics.rb`

Адаптирует исходную схему из восьми таблиц к общему аналитическому движку. `CanonicalDatabaseSource` строго проверяет схему, читает провайдеров, историю, очередь, решения и попытки, объединяет причины пропуска, проверяет целостность и отсутствующие связанные записи. `CanonicalDatabaseAnalytics` передаёт данные в общий `Analyzer` и дополняет отчёт подсчётом причин пропуска.

Используется `bin/analyze_db.rb`. Работает только на чтение, не создаёт и не мигрирует таблицы.

## Тесты

Все четыре файла используют Minitest. Тесты, меняющие данные, работают с временными копиями БД; проверки аналитического чтения также могут читать исходную базу и сверять её хеш. Наборы зависят от схемы и содержимого `DB/operations.db`.

| Файл | Что проверяет |
| --- | --- |
| `test/import_data_test.rb` | Перенос исходных файлов, сохранение схемы, существующих значений и ID провайдеров, загрузку примеров только по флагу, повторный импорт без изменений, откат при ошибке и запуск из другого каталога. |
| `test/provider_minute_stats_test.rb` | Границы минутного окна, часовые пояса, учёт всех статусов, нулевые значения, повторный пересчёт, сброс устаревшей статистики, некорректные даты и суммы, откат значений и новой колонки при ошибке записи, запуск CLI из другого каталога. |
| `test/canonical_database_analytics_test.rb` | Ожидаемые показатели отчёта для исходной базы, сохранение её хеша, корректный JSON и отклонение несовместимой схемы. |
| `test/routing_analytics_test.rb` | Импорт через `DatabaseWriter`, расчёты отчёта, замену решения при повторном журналировании, чтение без изменения БД, запись JSON и запрет записи в защищённые каталоги. Требует схему с `analytics_metadata`; на базе только из `DB/create_tables.rb` этот набор не рассчитан работать. |

Запуск каждого набора:

```powershell
bundle exec ruby -Ilib test/import_data_test.rb
bundle exec ruby -Ilib test/provider_minute_stats_test.rb
bundle exec ruby -Ilib test/canonical_database_analytics_test.rb
bundle exec ruby -Ilib test/routing_analytics_test.rb
```

## Совместимость команд

Для исходной схемы предусмотрена последовательность `DB/create_tables.rb` → `bin/import_data.rb` → `bin/analyze_db.rb`. Пересчёт минутных показателей изменяет схему, после чего строгий анализатор потребует адаптации.

Команды `bin/import_sources.rb`, `bin/log_operations.rb` и `bin/analyze.rb` используют другой вариант схемы с `analytics_metadata`. Скрипта подготовки этой схемы среди перечисленных файлов нет. Простого добавления одной таблицы может быть недостаточно: журналирование удаляет обработанные заявки из очереди, тогда как исходная схема связывает с ней решения и другие записи внешними ключами.
